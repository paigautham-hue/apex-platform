# data-model

> Last updated: 2026-04-21

## Purpose

Documents the canonical APEX data model: every table in
`drizzle/schema.ts`, the enums and JSON-typed shapes that live inside
those tables, the migration files that produce them, and the implicit
foreign-key relationships (APEX does **not** declare DB-level FKs —
every cross-table integrity check happens in `server/db.ts`). Every
other subsystem map depends on this one.

## Scope

- Files in this map: 6 (schema, relations, 4 migration SQLs + meta dir
  contents are excluded from orphan checks)
- Tables defined: 46
- Type exports: 92 (one `Select` + one `Insert` per table)
- Enums defined inline: ~25

## Internal Conventions

These conventions hold across every table. Violations are treated as
review-blocking bugs.

1. **Every tenant-scoped row has a `tenantId: int("tenantId").notNull()`.**
   Exceptions: `users` (tenant-agnostic; tied to auth provider) and
   `tenants` itself. The `userPreferences` table is also tenant-
   agnostic because preferences are per-user-not-per-tenant.

2. **Every table has `createdAt: timestamp().defaultNow().notNull()`
   and most have `updatedAt: timestamp().defaultNow().onUpdateNow().
   notNull()`** for change tracking.

3. **Primary keys are auto-increment ints.** `id: int().autoincrement
   ().primaryKey()`. No UUIDs anywhere — the system is small enough
   that ids are not a privacy concern and ints are faster.

4. **Indexes are named with the table name as prefix.** Pattern:
   `index("<tableName>_<fieldName>_idx").on(table.<fieldName>)`. The
   `tenantIdx` is mandatory on every tenant-scoped table.

5. **No foreign-key constraints declared at the DB layer.** Every
   cross-table integrity check is performed in `server/db.ts` (see
   `db-layer.md`). This is deliberate — Drizzle's FK support in
   MySQL has subtle issues and we'd rather catch in code.

6. **Enums are inline in the table definition** (`mysqlEnum("name",
   ["VAL1", "VAL2"])`) rather than separate constants. When an enum
   adds a value, both the schema declaration AND any narrowing
   `z.enum(...)` in routers must be updated in the same commit.

7. **JSON columns are typed via `.$type<...>()`.** The TypeScript
   type guards reads at the application layer but **does not enforce
   the shape at the DB layer**. If a row is inserted with the wrong
   shape (e.g. via a raw SQL migration), reads silently mistype.

8. **Type exports are paired: `<Table>` (select-shape) and `Insert<Table>`
   (insert-shape).** Always export both immediately after the table
   declaration. The insert shape allows optional fields with defaults
   and auto-generated ids.

9. **`successMetrics: json().$type<string[]>()`** (on `roles`) is the
   canonical "mandate list" surface. Don't model mandates anywhere
   else — `roles.successMetrics` is the canonical store. Future
   versioning (`roleMandateVersions`) will append, not replace.

10. **Decimal columns** (`metrics.targetValue`, `metricValues.actualValue`,
    `governanceAssessments.score`, etc.) come back from MySQL as
    **strings**, not numbers. Every read site must `parseFloat()` or
    `Number()` them. **This is a recurring bug source** — see Fragility
    Notes below.

## Fragility Notes

The most important section. Each note describes a real gotcha or
known bug pattern. New entries land as discovered.

### Decimal columns return as strings

MySQL `DECIMAL(P,S)` columns come back from `mysql2` (via Drizzle) as
**JavaScript strings**, not numbers. Affected columns:
`plans.weightPercentage`, `metrics.targetValue`,
`metricValues.actualValue`, `metricValues.targetValue`,
`governanceAssessments.score` (no — it's `int`, but the *display*
sites have mixed `Number()` calls anyway), `aiInsights.metadata`
nested score fields.

**The bug class this enables:** comparisons like `actual > target`
silently fall back to string-lexicographic ordering (`"100" < "9"`).
Arithmetic like `actual + diff` concatenates instead of adding.

**Defense:** Every read site that does math on these columns must
explicitly coerce: `parseFloat(row.actualValue ?? "0")` or
`Number(row.score)`. The recent Round-1 + Round-2 bug-fix passes
specifically tightened this in `ai-insights-generator.ts` and
`FinancialCockpit.tsx`.

### No FK constraints — orphans are possible

Because we don't declare DB-level FKs, an orphaned reference (e.g.
`persons.currentRoleId` pointing to a `roles.id` that was deleted) is
allowed by the database. Today nobody deletes `roles`, so orphans are
theoretical. But:

- `seed-evergreen.ts` doesn't truncate; it upserts. Running it twice
  is safe.
- If we ever add a "delete a person" flow, that delete must cascade
  in code: nullify `roles.personId` rows, soft-delete
  `governanceAssessments` rows whose `assessorPersonId` matches, etc.
- The audit-log pattern (per master plan §3.9) helps catch orphan
  creation when it accidentally happens.

### Schema-vs-Zod enum drift

When you add a value to a MySQL enum (e.g. add
`"DEFERRED_BY_PEER"` to `assessmentAssignments.status`), three places
need to be updated in the same commit:

1. The `mysqlEnum("status", [...])` in `drizzle/schema.ts`.
2. The corresponding `z.enum([...])` in `server/routers.ts` or
   `server/routers/*.ts`.
3. The client-side type union in any consuming page.

Missing one of these silently breaks: the DB accepts the new value but
the API rejects it, or vice versa. The MAPS-first workflow + tsc
catches most of these, but enums in JSON-typed fields slip through.

### Migration files are auto-generated — don't hand-edit

`drizzle/0000_*.sql` through `drizzle/0004_*.sql` are produced by
`drizzle-kit generate` reading `schema.ts`. Hand-editing them creates
divergence: the next `pnpm db:push` regenerates and your edit is lost.

**The right workflow:** modify `schema.ts`, run `pnpm db:push`, commit
both the schema change and the new migration SQL together.

### `tenants` is single-row today, but the schema is plural

The `tenants` table currently holds exactly one row (MEF). The schema
is plural because the architecture commits to multi-scope (§5.2) AND
to multi-tenant deployability when triggered (master plan §2 known
debt #1, §8 #6). All `tenantId`-scoped queries must continue treating
`tenantId` as a meaningful filter even though it's always `= 1` today.

### `agenticMemories` has rich fields not yet fully used

The Manus-built `agenticMemories` table includes `embedding` (json),
`subjectPersonId`, `subjectCompanyId`, `isPinned`, `validFrom`,
`invalidatedAt`, `keywords`, `linkedMemoryIds` — far more than the
current `server/agentic-memory.ts` consumes. These columns are
forward-compatible with Meridian's full system; Phase 3 wires them
up. **Don't drop columns thinking they're unused — they're planned.**

### JSON column shapes are not enforced at DB layer

A `roles.successMetrics` typed `string[]` can be inserted as any JSON
shape by raw SQL or a buggy code path. Reads will then mistype and
the consumer may crash. **Defense:** every write to a JSON-typed
column must go through the Drizzle insert/update path so TypeScript
catches shape errors at compile time. Avoid raw `db.execute(...)` for
JSON column writes.

### `selfReflections.visibility` is a tri-state

`PRIVATE` / `SHARED` / `IN_REVIEW`. Most read endpoints currently
ignore this field — they return reflections regardless of visibility.
Phase 1 Tier B + Phase 2 privacy-badge work will tighten this. **For
now, treat any read of `selfReflections` as a potential leak and add
a visibility check.**

### `notifications.type` enum drift risk

The existing 6 types (`PRIORITY_ZERO`/`INSIGHT`/`REMINDER`/
`MILESTONE`/`PULSE_CHECK`/`ACHIEVEMENT_SUGGESTION`) were chosen
before the governance events of master plan §5.7 were specified.
Governance events currently re-use `REMINDER` and `INSIGHT` via
`server/governance-notifications.ts`. When Phase 1 Tier C ships the
notification digest, decide: extend the enum or keep mapping
governance events onto the existing values. Either choice is fine —
just don't drift.

### `roles.successMetrics` is the canonical mandate list — don't model elsewhere

There is no `mandates` table. Mandates are strings in
`roles.successMetrics`. Anything that needs to display, count,
versionize, or AI-analyze a mandate reads from there. Future
versioning (planned `roleMandateVersions`) will append history, not
replace this column.
